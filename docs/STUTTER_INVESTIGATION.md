# 客户端卡顿排查记录

版本：0.2.24 起，2026-10-27 / 28 实测。本文只记录**有数据支撑**的结论，以及**已被排除**的方向，避免重复劳动。

排查工具全部是可开关的探针，默认关闭（`run/config/guidedrailways-server.toml` 的 `detailedLogging` / `performanceLogging`）。它们留在代码里，因为它们各自回答了一个别的东西回答不了的问题。

## 探针与它们回答的问题

| 探针 | 回答什么 |
|---|---|
| `[ClientPerf]` | 每个 5 秒窗口的 fps、**tps**、平均帧、最差帧、客户端 tick 耗时、GC 耗时与次数、堆占用、**最慢的渲染阶段** |
| `[FrameSpike]` | 单帧超过 40 ms 时的时间、堆、GC 次数、是否站在物理体上、窗口是否聚焦 |
| `[TickSpike]` | 服务端单个 tick 超过 45 ms 的时刻、在场车辆数与玩家数 |
| `[BogieRender]` / `[BogiePath]` | 转向架渲染器的每秒均值/峰值，以及两条绘制路径（native / fallbackRender）分别的耗时 |
| `[BerPerf]` | 本模组每个方块实体渲染器的每秒均值/峰值（bogie、coupler、console、nativeCoupler、dock） |
| `[SyncWatch]` | **客户端每秒收到多少次方块实体数据刷新**，按类型 |
| `[GuidedPerfSplit]` | 服务端物理步内部的分段耗时 |

## 已确认并修复的问题

| 提交 | 症状 | 根因 |
|---|---|---|
| `109504a` | **减速进站时 fps 从 100 掉到 50** | `MotionSync` 把任何浮点变化都当作“变了”，减速时每 2 tick 给 4 个转向架各发一次数据（40 次/秒），每次到达都让客户端重建该实体的视觉（GPU 上传）。改为每 8 tick、且只在变化超过 0.05 时发送；实测 `[SyncWatch]` 从 21~36 次/秒降到 4.6 次/秒，进站最低帧从 50 回到 78 |
| `7650d4d` | 长时间运行后偶发卡顿 | 控制台/车钩用 `sendBlockUpdated(..., UPDATE_CLIENTS)` 做纯视觉同步，客户端收到方块状态包会**重建该区块网格**。改为只发方块实体 payload |
| `06a9caa` + `f1017a2` | 列车首次进入视野时卡一下 | 转向架模型未烘焙就绘制，冷绘实测 **340 ms**。改为未烘焙当帧不画，并在客户端 tick 上按**方块实体**（不是按样式）预热 |
| `a66caac` | 默认款式（DEFAULT）转向架仍然冷绘 | 默认款式走 `StandardBogeyRenderer`，既没被预热也不会被“按样式预热”覆盖；`[BogiePath]` 的 fallback 分支计时也写错了（记的是 native 尝试的时间）。已改为按该渲染器预热并单独计时，峰值 82 ms → 31.8 ms |
| `56307b5` | 崩溃守卫自身开销 | `BodyGuard` 在物理步的三个位置各探测一次、每次探测 2 个刚体，而一个 tick 有多个子步。改为每个刚体每 tick 只探测一次 |
| `41e6353` | 每子步分配 | `mayPass` 通过 `memory.active()` 建 List 再 stream；`CouplerJoint` 在日志门控之前就建两个世界坐标并扫描全部玩家 |
| `f450ff3` | 每帧分配 | 控制台渲染器每帧构造 3~4 个 `ResourceLocation`；预热请求在排队期间每帧复制一次 `CompoundTag` |
| `e719dc7` | 每帧分配 | 车钩渲染器对每个 box、每一帧都拼接字符串并解析贴图 ID |
| `81ecdf2` | 停站等待期间的开销 | 停站时每 tick 重新评估时刻表条件，而乘客条件会**扫描全服玩家**并逐人做 Sable 包含查询，货物条件会重建容器快照。改为每 5 tick 评估一次 |

整体效果（同一套探针、同一玩法，5 秒窗口统计）：

| 指标 | 排查前 | 现在 |
|---|---|---|
| 单帧 >40 ms 次数 | 166 | 54 |
| 最差帧中位 | 236~285 ms | 33~123 ms |
| 巡航 fps | 45~59 | 95~113 |

## 已排除的方向（有数据，不要再查）

| 方向 | 证据 |
|---|---|
| 服务端 TPS | `[ClientPerf] tps` 稳定 19.5~20.7；`[TickSpike]` 只有加载期几次 |
| 服务端单刻耗时 | 稳定期 1~9 ms |
| GC / 内存 | 堆上限 12 GB、实际用 5~7 GB，稳定期 GC 0~40 ms、次数 0~3 次/5 秒 |
| 地形区块加载 | 渲染距离 12 → 8 只把最差帧中位从 285 降到 236 ms，且环线运行时没有新地点 |
| Flywheel 实例化后端 | 关掉（`flywheel:off`）后反而更慢（转向架峰值 133 → 334 ms） |
| 本模组的四个渲染器 | `[BerPerf]` 实测 bogie ≤31.8（首帧后 1~3）、coupler ≤4.3、console ≤0.8、dock ≤1.8 ms |
| 日志写入 | JFR 采样中渲染线程**没有**任何日志/IO 栈帧 |
| 本模组的 Java 热点 | JFR 的 457 个渲染线程样本里，最高自身耗时只有 54 个样本（≈1.1 s，分散在几百帧）；栈内出现 `com.guidedrailways` 的样本只有 1 个 |
| 线程阻塞 | JFR 的 `ThreadPark` / `JavaMonitorEnter` 中渲染线程没有长阻塞 |

## Xaero 小地图：保留，但需要降开销

移出 Xaero 后 fps 从 45~59 直接涨到 **95~113**，平均帧从 8.7~20.2 ms 降到 1.7~5.9 ms——它是剩余开销里最大的一块，且**每帧**都在花。因此本项目选择保留小地图、但降低它的成本（`run/config/xaero/minimap/profiles/default.cfg`，本地开发配置，不入库）：

| 设置 | 值 | 理由 |
|---|---|---|
| `display_radar` | `false` | 实体雷达每帧扫描并绘制附近实体点，是最贵的一项；关掉后小地图与地形仍然可用 |
| `minimap_terrain_depth` | `false` | 地形深度着色需要逐像素处理 |
| `minimap_terrain_slopes` | `0` | 坡度着色同样逐像素 |

改动前的原文件备份为 `default.cfg.bak-perf`。若要恢复小地图的完整观感，把这三项改回 `true` / `2` 即可，代价是 fps 回到 45~59。

## 遗留：仍然存在但已不构成体感问题的开销

剩下的偶发长帧（单帧 150~500 ms，5 秒窗口内 0~2 次）落在**其他模组**的渲染阶段：

- `minecraft:after_solid_blocks`：地形方块层（区块网格上传）
- `aeronautics:levitite`：Aeronautics 的自定义渲染阶段

本模组在这两段里只占 ≤5 ms。继续追需要修改上游模组的渲染路径，超出本仓库范围。

## 同一形状的功能缺陷：永久锁定状态

排查卡顿时发现的一类问题值得单独记下来，因为它和“性能”无关却表现得一模一样：**命令正常、力 ≈ 0、车不动**。四个案例都是“某个状态只能由正常路径清除，而没有超时”。

| 状态 | 症状 | 处理 |
|---|---|---|
| `Room ≈ 0`（站在岔口上） | 停车模型按住不放，而离开岔口必须移动 | `54e8409`：room 小于蠕动阈值时按“未知限距”交给停车模型（它对此的语义就是给牵引力） |
| `SwitchReservations` 旧预约 | 同一列车被自己的旧路线挡住，264 tick 不动 | `d53ba92`：陈旧（半寿命未刷新）的自我预约可被新路线接管 |
| 驾驶使能 `enabled` | 时刻表启动后关掉，手动推杆无效 | `76cb830`：手动给档位即接管使能 |
| `MountEntity.handoff` | 交接永不完成 → 该转向架永不初始化、永不输出牵引 | `0ed5ec6`：记录写入时刻，200 tick 未解决即放弃并记 `[MountHandoffExpired]` |

**未修但已知**：`CouplerHandoff` 同样没有年龄，但它承担“防止所有权被盗”的语义，直接加过期会在“搬移比超时更慢”时让源端失去保护，反而引入新的归属错误。建议规则：只在“目标端不存在且源端未移动”时标记 `abandoned`，保留 `protectsSource` 仍为真，并允许玩家手动重新连挂解除。这条需要玩法决策，故留待后续。

## 复现方法

1. 打开 `detailedLogging` 与 `performanceLogging`
2. 进游戏跑一趟进出站，保持 1~2 分钟
3. 读 `run/logs/latest.log`：
   - `[ClientPerf]` 看 `tps`、`frameWorstMs`、`worstStage`
   - `[SyncWatch]` 看客户端每秒的方块实体刷新次数（正常应 ≤8）
   - `[BogieRender]` / `[BerPerf]` 看本模组渲染器峰值（正常应 ≤5 ms，首帧除外）
