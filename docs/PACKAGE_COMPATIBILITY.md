# 包裹取件与派送

0.2.22 已移除整列任意可写容器交换，邮件改为实际对接的原生缓冲与关联邮箱之间传递；车载箱子需接入真实输送路径。当前边界及集中验收见 [货运访问边界](CARGO_ACCESS_BOUNDARY.md)，下文保留早期实现背景

版本：0.1.49 · Create 6.0.10-280 · Minecraft 1.21.1

0.1.49 起实际邮箱交换须通过铁路对接连接器验证，取件/派送选站限于已绑定铁路端点的车站。下文的包裹规则继续适用，安装与对接条件以 `RAIL_DOCKING.md` 为准；不再支持无对接直接在停站时搬运包裹

## 已接入的行为

- 原版 `FetchPackagesInstruction`：按包裹地址筛选有外发包裹的车站，再从可达车站中寻路。空白筛选沿用原版通配规则，筛选的是包裹地址而非车站名称
- 原版 `DeliverPackagesInstruction`：读取整列车载包裹，寻找关联邮箱的地址能接收这些包裹的车站。无车载包裹时跳过该条；有包裹却没有匹配车站时保留任务并重试
- 单条取件/派送指令访问一站，随后执行该条的等待条件并进入下一条。需要走访多个目的站时，可重复派送条目或使用循环表；不是自动送完所有地址才结束单条指令
- 到站方式沿用物理列车的现有寻路、双向进站、信号停车与稳定停车判断，没有创建替代 Create Train
- 停稳且铁路连接器验证对接后，在已关联的原版邮箱与整列可写车载库存间交换实际包裹。绑定了铁路端点的普通目的站条目也参与交换；仅在自动驾驶确认到站后进行，手动停车暂不自动交换
- 先卸下寄往本站邮箱的包裹，再装上寄往其他地址的包裹。取件地址筛选决定去哪站，实际到站后会交换该站所有可交换邮件，这与原版区分选站筛选和停站交换的做法一致
- 整列存储包含连挂拖车，同一车体多副转向架不重复统计。完整保留包裹物品组件，不拆封、不重建内容
- 一次交换每个方向最多处理 64 个包裹槽位，每 20 tick 重试；包裹任务有本站未装卸完的邮件时保持等待，再检查时刻表条件。普通目的站按自己的条件决定发车
- 实际交换立即刷新货物快照并记录活动，可配合装卸空闲条件使用。有效铁路对接下，已加载、关联有效的邮箱可为本次停站提供明确的交换记录，无需额外安装软管才能判断此次邮件交换的空闲
- 已加载邮箱沿用原版保存与离线缓冲同步路径，并发出成功交换的 `package_sent` / `package_received` ComputerCraft 事件和粒子。没有实现其他列车 ComputerCraft 查询接口

## 存储边界与恢复

车载自动交换要求存储提供本地 `IItemHandlerModifiable`，常规箱子、桶、潜影盒等 `Container` 使用本地 `InvWrapper`。多方块存储沿用货物扫描器的控制器去重。只暴露只读接口或不提供可修改槽位的存储仍可参与数量统计，但不被直接写入。Simulated 对接连接器的缓冲区不会作为本功能的写入端，可先由连接器或管线输送到车载箱子。

交换只使用空目标槽位，先模拟检查完整提取、有效物品和完整放入；不做部分插入或合并包裹。直接槽位写入保留整个物品栈，失败时尝试恢复两端原槽位并让自动驾驶异常保护暂停。此项依赖库存遵守 NeoForge 修改接口契约，不能保证对任意行为异常的第三方处理器都能恢复。双方同时装满时需要腾出空槽，不做强制交换。

原版邮箱通过车站关联关系识别，单纯放在车站附近不算关联。车载邮箱不作为站台侧端点。已有原版列车占用该站时，本功能不会同时交换其邮件。

未加载邮箱的离线缓冲仅作为取件寻路的只读线索。到站后若相关邮箱仍未加载或关联尚未恢复，列车等待，不直接写离线缓冲、不强制加载区块。未知邮箱内容不能被当成“没有包裹”跳过任务。这比原版对离线邮箱的处理更保守，不应描述为已完整兼容离线包裹运输。

等待状态、条目、目标车站及条件进度使用既有时刻表持久化。重载后等待原编组恢复，并重新读取真实库存。已经到站等待的任务保持原目标，不会因包裹刚卸完而在重载时选到另一站；已完成的等待步骤保留。运行中连挂/解挂沿用暂停保护，重新继续后接受新编组。

## 待进行的客户端测试

1. 建立两个相连车站 A/B，各关联一个原版邮箱，地址分别为 A/B。A 邮箱放寄往 B 的包裹；物理车体上装普通箱子，提供动力，插入“取件 B → 等待 3 秒 → 派送 → 等待 3 秒”的时刻表，检查在 A 取件、在 B 收件
2. 包裹放入后挂车厢、同车体装两副转向架，再测试无转向架的连挂货车，确认整列选站、装卸和计数各一次
3. A/B 地址使用原版支持的通配写法，分别测试空白取件筛选、精确筛选、其他地址和无包裹。没有匹配取件任务应跳过；有包裹但没有匹配收件站应等待，新增收件站后可重试
4. 箱子或邮箱装满、提取/插入受限、包裹位于只读缓冲区时，确认包裹不丢失、不重复、不替换普通物品。腾出空槽或把缓冲区邮件送入可写箱子后恢复
5. 普通目的站条目停站也应交换邮件；包裹任务装卸后执行延时、人数、数量或装卸空闲条件。持续邮件交换不能提前满足空闲条件
6. 同站多个邮箱、车站端收发同时存在、多个地址混装，检查只卸匹配地址，留在邮箱的收件不会又被装回列车，重复停站不复制包裹
7. 取件途中、已到站等待、因空间不足等待时分别退出重进，确认包裹总数、目标站和等待步骤保持；重载后空闲计时重新观察
8. 临时卸载邮箱区块或延迟加载拖车，不能把未知库存当空；恢复加载后继续。编组变化应暂停，重新继续后按新编组统计
9. 与原版列车混跑并停靠同站，检查信号停车和邮件归属；已加载邮箱的粒子、比较器及 ComputerCraft 成功收发事件正确
10. 中英文驾驶台状态不溢出，无翻译键泄露；日志关注 `[AutomaticRoute]`、`[PackageMail]`、`[ScheduleCondition]`、`[ScheduleRestored]` 及异常堆栈

## 自动检查与实际验收

`checkPackageMail` 覆盖空任务、无收件目标、未知库存、整列收发、地址过滤后的转移、满仓、提取/插入限制、重复停站、预算、包裹身份守恒及单次端点写入异常回滚。还运行语言检查和完整离线构建。

检查不启动 Minecraft；实际包裹物品、邮箱关联、Sable 车载能力、ComputerCraft 事件及存档闭环尚待客户端验收。尚不能将这一步视为整个铁路系统或全部包裹功能已兼容。
