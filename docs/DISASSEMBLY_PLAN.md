# 物理列车拆解与重新组装方案

日期：2026-11-02。状态：设计提案，尚未实现。本方案中的行为与组件名称均为拟议设计。

## 目标与当前依据

沿用 Create 车站的拆解操作，把停稳的物理列车还原为可编辑的世界方块，再通过物理组装恢复运行。拆解不是销毁车体并掉落全部材料，也不是把列车转换成原版 Train。最终交付必须完成“停车 → 拆解 → 修改方块 → 重新组装 → 行驶”的闭环。

当前 StationBlockEntityMixin 拦截物理列车的车站组装及拆解，PhysicalStationScreenMixin 禁用对应按钮；PhysicalTrainProxy.canDisassemble/disassemble 均返回 false。代理仍应保持只读，新增操作由实际物理后端执行，不调用原生 Train 的拆解算法。

现有 ConstructionTransaction、MoveBatch、BlockAssembly 可借鉴预检和逆序恢复方式，但不具备完整列车迁移、持久化恢复或第三方副作用回滚能力。Sable 的本地公开 API 提供 moveBlocks、moveOtherStuff、moveTrackingPoints 等迁移入口；具体方块实体、挂载关系、乘客和移动回调的行为仍需专项验证，不能仅凭方法签名认定可直接安全拆车。

## 玩家流程

1. 列车在普通车站停稳，玩家暂停时刻表、松开外部对接并让乘客离车。
2. 打开原版车站界面，点击“拆解列车”。服务端生成方案，显示目标区域预览；不能拆解时给出具体阻挡原因。
3. 玩家确认预览。服务端再次核验同一列车、编组、位置和空间后执行。多个玩家的重复请求只能提交一次；不能使用客户端提供的方块清单作为权威数据。
4. 成功后，车体变为原位附近、按世界网格对齐的静态结构，箱子、流体、驾驶台及其时刻表保持内容，名称和设置保留。运行进度保留为暂停状态，不自动发车。
5. 玩家编辑静态结构后，通过同一车站的物理组装入口恢复。重新读取实际结构和粘合关系，不能把拆解前的快照覆盖回来。仍需检查驾驶台、转向架、轨距、空间及编组有效性。

界面沿用 Create 样式；不新增拆车机器。按钮文案、失败原因与预览需遵循项目语言规范，中英文同步。预览仅在请求时生成，平时不逐 tick 扫描整个列车。

## 首版范围

- 平直、水平轨道，整列车体完整加载，全部转向架导向关系有效；每节车厢具备一致的世界网格映射。
- 整列拆解。首版不允许隐式拆开连挂中的局部车厢；要单独处理先显式解挂。
- 拒绝曲线、坡道、脱轨、跨维度、未恢复完整的车钩关系、未加载成员和不能可靠迁移的外部约束。
- 必须实际停稳并且没有驾驶员接管、登乘乘客、已锁定的对接器或运行中的包裹交换。卸货未完成或外部红石锁未释放时说明原因，不强行拆掉另一端设施。
- 目标空间不得覆盖轨道、车站、已有建筑或另一物理车体。首版只接受空气与明确允许的可替换目标，不把“状态相同的现有方块”当作免费可占用位置；含物品或流体的目标不可覆盖。
- 遵守服务端距离、权限和保护规则；第三方领地保护是否生效需要对应集成测试，不能只检查一个方块位置后批量绕过。

限制会直接显示给玩家。首版不承诺任意位置的自动扶正、远程拆车、自动下客或紧急回收。

## 世界方块与转向架映射

普通车体使用每节车厢统一的格点变换，方向属性随正交旋转变化；不能逐块取整，也不能让车体与其转向架分别取整后改变安装间距。小幅对齐应通过预览明确表现，无法得到一致映射则拒绝操作。

必须先验证现有构架及安装座能否作为静态世界组件正确表示和重新组装。现有转向架的独立下部刚体及辅助碰撞单元不能原样当作普通建筑材料复制出来，也不能简单删除后额外赠送一个转向架物品。采用明确的组件映射：每个真实转向架只生成一套静态表示，保留轨距、款式及有效安装关系；辅助碰撞单元由款式重新生成，不额外产生材料。

如果现有方块不能承担静态表示，先补充与现有转向架对应的静态表示及重建规则，再开放拆解。首次技术验证必须证明这条往返路径，不能等到最后才发现拆下来的车无法重新组装。

箱子、水箱、对接器缓冲、驾驶台物品和方块实体数据随实际方块迁移，调用并验证所需的移动回调。避免破坏掉落与方块复制同时发生。动力网络、管道、车钩地址及第三方 capability 必须重新绑定；旧视图在提交后失效。原生代理运行期 UUID 不作为静态建筑身份复用要求。

## 提交与失败恢复

拟采用一次服务端操作标识，集中管理拆解生命周期：预检 → 短期锁定 → 再校验 → 迁移 → 提交 → 清理。短期锁仅属于本次操作，不变成永久列车锁。

预检记录编组成员、实际方块与方块实体、安装关系、目标映射及必要恢复数据；不修改世界、不释放信号占用。确认后复查版本、位姿和目标空间，暂停驾驶推进与本次相关的输送写入口，再开始迁移。玩家在预览期间改变编组、建筑或列车位置，旧方案必须失效。

迁移过程中保留源数据的唯一权威归属，不能让源和目标同时向玩家、漏斗或外部 capability 开放同一份库存。具体做法需由 Sable 迁移接口验证决定；同一 tick 内执行不能替代对回调及第三方写入的防护。单次工作量需有上限，超过上限先拒绝；若以后分批执行，未完成数据也不得成为可交互的半列车。

只有目标结构及数据完成校验后，才删除对应源刚体并注销运行身份、车站关联、信号占用、观察器成员、地图标记和对接请求。不能先清空占用，再让旧车体长时间留在铁路上。清理仅作用于本列车，不清除其他列车的预约或外部红石锁。

普通异常恢复源车体和关联、撤销本次目标写入，列车保持停车，提示玩家处理问题后主动恢复。恢复本身失败时禁止继续生成物品或重新提交，保留操作记录及可诊断的恢复数据。

持久化操作记录必须设计并注入中断验证，重进后检查源、目标和提交阶段，不能同时恢复两套材料。世界区块、Sable 与 SavedData 并非天然跨文件原子事务；正常异常回滚通过不等于断电安全。最终恢复能力按实际测试记录，不预先承诺任意断电无损。

## 实施顺序与验收门槛

1. 技术验证：一节空车往返迁移，证明统一网格映射、静态转向架、安装座、辅助碰撞单元和重组装可行；再加入带内容箱子、水箱与驾驶台。优先解决组件表示，不先放开按钮。
2. 后端：实现完整预检、操作锁、目标冲突检查、迁移和异常恢复；接入已有身份、信号、车钩、对接及输送失效清理。原生代理直接拆解仍拒绝，所有实际操作进入同一协调入口。
3. 玩法闭环：车站按钮、预览、确认、原因提示、物理重新组装与语言检查。物理静态结构不能误走原版 Train 组装路径；普通原版列车继续沿用原流程。
4. 隔离测试及用户游戏验收：完成后才扩大到多车厢或更复杂轨道。测试服务端与客户端均按项目约定和用户授权启动。

必要场景：

- 空车、带物品/流体、不同转向架款式；拆解、编辑、重组装后数量和有效设置守恒。
- 多车厢、同一车体多副转向架；同款组件没有重复生成或重复回收，重新组装后安装间距正确。
- 目标被占、未加载、坡道/弯道、移动中、乘客未离车、对接未释放；拒绝后无方块、库存和占用变化。
- 两名玩家同时操作、旧预览重放、迁移时源/目标发生变化；只允许一次有效提交。
- 在写入、源移除及清理阶段注入失败，核对可恢复性、数量守恒和占用，不能只验证正常路径。
- 拆解前后保存重进、操作中断后的恢复；检查原生代理、地图标记、车钩记录、对接锁及 capability 不残留。
- 原版列车原有组装/拆解回归；安装及未安装 Simulated 等可选兼容时的类加载与边界回归。
- 工作量达到上限时仍能及时拒绝；确认后不能形成长时间阻塞服务器的整列全量复制。

这些是计划验收项目，当前均未因本文档而视为已通过。
