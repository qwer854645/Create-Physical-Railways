# 故障、卸载与重启服务端验证

日期：2026-11-11。基于 `8001bcf`，包含本轮发现的缺轴保护修正。
本轮用户明确要求自行测试，使用独立 GameTest 服务端；没有打开客户端，也没有读写玩家存档。

## 环境与复现

- Minecraft 1.21.1、NeoForge 21.1.264、Create 6.0.10、Sable 2.0.6。
- 加载本机完整开发依赖组合，包括 Railway、BnB、Electro Energetics、Aeronautics/Simulated 和 Xaero。
- 场景位于 `build/signal-validation-run`；普通运行只清除此目录的 `world`。
  第二阶段显式保留同一个测试世界，要求已有世界和 `fault-restart.properties`，不接受任意外部世界路径。

复现第一阶段（新建世界、故障与加载测试、保存）：

```powershell
.\gradlew.bat runSignalValidation -PsignalServerTests --offline
```

待进程正常退出后，复现第二阶段（新进程重新加载上一阶段世界）：

```powershell
.\gradlew.bat runSignalValidation -PsignalServerTests -PvalidationRestart --offline
```

`src/faultValidation` 仅在显式启用服务端测试时加入开发运行的生产模块，以访问包内控制边界；
它是独立 source set，不进入发行 JAR。其他夹具仍由独立验证模组加载。
不要同时运行两阶段，也不要在两阶段之间执行 `clean`。

## 发现与修正

1. 初次复跑中，旧时刻表夹具在强制加载区块尚未进入实体 tick 时就开始检查，导致前提断言失败。
   改为等待实际实体 tick 就绪，再启动与原版同步的延迟计时；原版一秒延迟仍在第 21 次检查完成。
2. 实车测试发现：车体和连挂关节仍存在、尾车转向架已经卸载时，货运完整性检查仍可能为真。
   原恢复检查只遍历当前单位，漏掉已经消失的尾轴，整列没有进入等待保护。
   `TrainFaults.begin` 现比较上一刻编组的车体与轴 UUID，发现缺员后保留原集合并进入恢复窗口；
   明确的主动编组操作才更新基线。修正前同一实车场景失败，修正后通过。

## 实车结果

两条独立的真实 Create 直轨上分别放置一列两车厢物理列车和一辆独立物理车。
使用正常转向架放置、32 RPM 创造马达、驾驶台时刻表、真实车钩关节和两份实际箱子库存。
没有注入速度、占用、制动力或车辆位置。

- **故障隔离通过**：在已运行的两车厢列车中，将缓存指令替换为不支持的具体类型，
  由真实自动控制异常边界触发故障保护。两个车厢停止接受正牵引，时刻表暂停，另一列保持运行。
- **实际制动通过**：故障后第 60 tick，两个车厢的最大速度约 `0.00081` 格/秒，
  此前已连续 20 tick 低于 `0.1` 格/秒；车头参考点移动约 `0.83` 格，另一列前进约 `9.19` 格。
  这只是本场景的结果，不是通用停车距离保证。车辆均未脱轨，货物、配对和项目进度保留。
- **部分卸载通过**：用 Sable 原生接口卸载尾车转向架，10 tick 后确认原生对象不存在、
  编组只剩一副活动轴且整列被保持；自动运行意图仍保留。用真实序列化数据恢复原生刚体后，
  第 30 tick 解除保持，随后两车厢恢复实际移动。此处是 API 控制的局部卸载，不代表所有自然区块流送时序。
- **整个服务端重启通过**：第一阶段保存两节车、箱子和暂停的时刻表，然后让服务端正常退出。
  新 JVM 载入相同世界，核对四个物理体 UUID、驾驶台位置、两个箱子各 17 个钻石、
  车钩链接 UUID 和 Create 列车身份均不变，真实连挂关节重建完成。
  时刻表保持暂停，玩家入口继续后，100 tick 内车头前进约 `9.22` 格，两节车速度均约 `3.04` 格/秒。

既有信号 API、岔口图、分批索引、时刻表条件/显示和两组原版/物理直轨混跑也共同通过。
保存轮为 `All 8 required tests passed`、`BUILD SUCCESSFUL in 43s`；
重启轮为 `All 8 required tests passed`、`BUILD SUCCESSFUL in 36s`。
两轮均正常保存、退出，没有遗留测试服务端。

## 恢复检查开销

使用正常放置的 1、8、32 列静止独立物理车，每列一副转向架、两个未连接的车钩端点；
32 列对应 64 个原生刚体。每档等待 60 tick 后，在真实服务端调用生产恢复检查，
每 tick 调用 20 次，丢弃前 100 次预热，保留 500 次计时；测量后恢复完整世界查询映射。
这是正常就绪状态的 Java 方法微测，不是整体服务器 tick、故障重建或 FPS 压测。

两次保存/重启轮的结果接近：

- 1 列：平均约 `0.0005 ms`。
- 8 列：平均约 `0.006 ms`。
- 32 列：平均约 `0.099 ms`，P95 约 `0.12 ms`，最大约 `0.15 ms`。

重复端点遍历仍具有随规模放大的风险，但本场景没有证据显示它是明显卡顿来源，
暂不以此为由扩大索引重构。该结果不能推导客户端 FPS、原生物理求解成本或长时间内存趋势。
