# 机械动力铁路兼容性检查

检查日期：2026-10-19 · 参考依赖：Create 6.0.10-280 / Minecraft 1.21.1

## 结论

**尚未达到“完全兼容机械动力铁路系统”的目标**

现阶段是使用 Create 轨道图、部分时刻表数据及部分铁路设备接口的独立物理列车。接口接入和构建通过不能替代游戏内验收。当前代码版本为 0.1.53；基础时刻表扩展、存档恢复、渲染包围盒修复及观察器基础检测已完成代码与自动检查，仍待客户端验收。

检查依据为本项目源码、锁定版本 Create jar 内的公开类及接口、现有自动检查和已有用户测试反馈。本次没有启动客户端或自行开启服务器。

Steam ’n’ Rails 可选适配的新增范围与独立验收清单见 [STEAM_RAILS_COMPATIBILITY.md](STEAM_RAILS_COMPATIBILITY.md)，不改变上述完整兼容性结论

## 0.2.21 身份、车站、导航与显示进展

已加入原生 Train 查询代理与独立身份持久化，仅含有效主驾驶台的编组会发布。服务端/客户端可查询 UUID、逻辑车厢、位置、速度及真实关联的停靠车站。0.2.15 将停稳结果接入 GlobalStation 的实际列车关联，并移除旗帜和比较器的独立覆盖。0.2.16 同步原生 Navigation 目的地、距离、方向及未来分叉，并投影 ScheduleRuntime 时刻表、暂停、项目和等待进度；原生执行入口隔离，实际控制仍由物理后端负责。0.2.17 向原生车站信息显示提供当前已确认目的站的记录，根据实际行程进度估算到站时间；没有发布未规划后续站或不确定等待条件的时间预测。0.2.18 从主驾驶台编辑并保存整列名称，同步到两端原生身份与信息显示。0.2.19 记录新驾驶台放置者并同步原生 Train.owner，未知历史保留未记录，不增加驾驶权限限制。代码和离线检查不代表地图和铁路扩展自动全部兼容。具体边界和验收步骤见 [原生身份桥接](NATIVE_TRAIN_IDENTITY.md)。下列旧版本记录保留其历史验收背景。

0.2.20 增加服务端原生车厢货物只读 handler 和 /physicalrailways cargo 查询，不复制原版挂载库存或增加原版可移式接口装卸。0.2.21 让实际覆盖的列车观察器按整列物品/流体过滤，并通过原生 keepAlive 关联已有列车 UUID；未知库存不匹配。过滤、红石与外部信息读取尚待游戏内回归，详见上述桥接文档。

## 分项结果与验收要求

### 1. 同维度固定轨道：已接入，完整场景仍待验收

`TrackNetwork` 读取 Create 原生轨道图，处理直轨、贝塞尔弯轨及节点连接。`ConsistRoutes` 和 `RouteMemory` 让编组轮轴沿头车选路行驶。自动寻路使用 `AutomaticNavigation` 与 `ScheduleRoute`。

验收要求：直线、坡道、连续弯道、交叉、分岔、反向运行，以及长编组通过后折返，均不误选其他线路。轨道删除和连接变化后的行为也须验证。几何测试通过不代表全部物理场景通过。

### 2. 跨维度铁路：未实现

`TrackNetwork` 与 `AutomaticNavigation` 明确跳过 `isInterDimensional()` 边。`CouplerConnections.beforeMove` 在跨维度移动时解挂。

验收要求：整列按顺序通过传送门，车钩、动力、旅客、物品、控制权、时刻表、区段占用与到站状态连续有效；不能只传送头车。

### 3. 时刻表物品和基础导航：部分实现

支持原版时刻表物品装入、取回、悬停查看，以及目的站名称匹配、进站、暂停、继续、跳过与重新开始。

`ScheduleController.unsupported` 仅接受：

- 指令：`DestinationInstruction`、`ChangeThrottleInstruction`、`ChangeTitleInstruction`、`FetchPackagesInstruction`、`DeliverPackagesInstruction`
- 条件：`ScheduledDelay`、`TimeOfDayCondition`、`StationPoweredCondition`、`RedstoneLinkCondition`、`ItemThresholdCondition`、`FluidThresholdCondition`、`IdleCargoCondition`、`PlayerPassengerCondition`

调整运行速度按比例限制自动驾驶目标速度，显示标题同步到驾驶台设置界面；两者运行状态随存档保持。车站供电条件使用当前目标站，红石连接使用原版全局频率网络；没有伪造原版 Train。上述新增功能待客户端验收，因此不能声称兼容任意原版时刻表。

### 4. 时刻表其余指令和条件：仍有未实现项

锁定版本 Create 中可见、当前未接入的功能包括：

- 车站卸载相关条件：`StationUnloadedCondition`

验收要求：逐项明确输入、效果、暂停/恢复、分支 AND/OR 语义及存档行为。不能把需要原版 Train 的条件直接传入空 Train 调用；现有代码已经刻意禁止这种做法。

### 5. 车站到达表现：部分实现

`StationPresence` 在 0.2.15 起建立实际原生车站关联，到站旗帜及比较器由原版车站更新，相关独立覆盖已删除。此前用户已反馈自动入站通过，但长编组、重载、混跑等仍需回归。

0.2.13 起物理列车以只读 `Train` 代理注册，0.2.15 已将实际停靠关联接入 `GlobalStation.getPresentTrain()` 等入口；完整列车编辑、原版自动时刻表及所有外部查询尚未适配。原版组装入口对物理列车给出提示并阻止进入，不能计为已兼容原版组装流程。

验收要求：确定物理列车身份、名称和编组数据如何供车站及其他设备读取；到站、离站、换站、同名站、自动发放时刻表、站台偏移及重载行为有明确对应。

### 6. 信号、区段占用与混跑：首版已实现，尚未完成游戏内验收

`PhysicalSignals`、`SignalOccupancy` 和 `SignalEdgeGroupMixin` 接入区段占用、交叉冲突、制动范围内预约、红石强制红灯与链式出口检查。自动驾驶等待后可以继续原时刻表；手动驾驶当前仅上报占用，不强制执行红灯停车。

现有自动检查主要覆盖账本及制动模型，不能证明与原版列车混跑、所有链式信号布局、原版预约时序均正确。尚无拥堵绕行、预约公平队列或死锁恢复；跨存档尚未持久化离线车辆的区段占用，复杂编组的占用范围采用保守近似。

验收要求：红灯与恢复、追踪间隔、长车尾部释放、双向冲突、交叉与链式出口、与原版列车互相等待，以及暂停、卸载和重载时无错误放行或永久占用。

### 7. 列车观察器：基础检测已接入，待客户端验收

`PhysicalObservers` 和 `TrackObserverMixin` 按物理列车覆盖的轨道区间刷新原版激活计时器，沿用 `TrackObserverBlockEntity` 的红石输出与方块状态更新。相邻帧轮轴区间补充高速通过检测，支持倒退与停车持续检测。

检测复用车体、连挂编组的轨道覆盖估算，车体端部越过节点后的延伸不向所有岔路触发；复杂环线、长编组和节点附近仍需回归。没有合成原版 Train，未提供物理列车 UUID 给原版设备；ComputerCraft 列车事件及显示链接的车名、目的地等尚未接入。设置了过滤物品的观察器暂不检测物理列车，货物过滤仍未实现。

验收要求：按方向、整列通过及过滤规则触发输出，兼容停车、倒退、长车和重载，不把每个转向架误计为一列新车。

### 8. 显示链接、原版列车管理和外部查询：未完整接入

当前没有物理列车到原版列车身份/数据查询体系的完整桥接。单独接入信号和到站状态不会自动带来目的地、车名、预计到达、时刻表标题等显示信息，也不会自动适配 ComputerCraft。

验收要求：列出原版信息源和查询入口，按统一的物理列车身份提供真实数据。第三方扩展需单独界定兼容范围。

### 9. 货物、流体、包裹与旅客：未完成铁路层面的兼容

0.1.44 已接入整列物品/流体数量条件与限定输送路径的装卸空闲记录，可选适配 Hose Connectors、Simulated 对接连接器和 Automated Logistics 的货运统计。支持范围与待测场景见 `CARGO_COMPATIBILITY.md`，尚未经客户端验收；这不代表 Create 原版可移式接口已兼容 Sable。0.1.45 进一步接入整列 Create 座椅的玩家乘客等待条件，范围及测试清单见 `PASSENGER_COMPATIBILITY.md`，仍待客户端验收。0.1.46 已接入包裹取件/派送寻路；0.1.49 将邮箱交换统一经过新增铁路对接连接器的有效对接校验，支持车站绑定、实时地址和自动锁定释放。详见 `PACKAGE_COMPATIBILITY.md` 与 `RAIL_DOCKING.md`。离线邮箱写入、手动停车交换、跨维度旅客迁移及任意第三方容器的完整适配仍未完成，新增代码尚待客户端验收。

验收要求：整列货物统计、跨车厢装卸、数量与空闲条件、包裹任务、上下车及卸载/重载后的内容保持一致。

### 10. 编组、碰撞、存档与渲染：已有实现，但存在未关闭的问题

车钩、统一主驾驶台、多转向架、原版模型复用等已实现。用户近期报告的实际问题表明稳定性仍未达到验收要求：

- 手杖拖动碰撞后卡住：0.1.40 已替换转向架之间的接触方式，仍需用户确认效果
- 退出重进后时刻表不继续或进度不对：已保存运行状态、原编组和等待进度，重载稳定后恢复；待客户端验收
- 退出保存异常：日志存在 `Cannot change blocks in nonexistent plot holder`，调用链经过 `setRemoved`、`DriverControls.removed` 和制动数据发送；已分开卸载/拆除，并禁止卸载车钩时发送方块更新；待退出保存回归
- 视野边缘消失：BogieEntity 默认渲染包围盒仅覆盖中心方块，而模型超出该范围；已按完整碰撞模型范围扩大渲染包围盒；待客户端确认

验收要求：多次退出重进、部分车厢延迟加载、连挂/解挂、移动车体、拆除主控和边缘视野观察后，配置、进度、身份与显示都保持正确，日志无保存异常。

## 后续顺序

1. 先关闭退出保存、时刻表恢复和边缘裁剪问题，回归碰撞及基础运行
2. 对基础车站与信号做实际客户端验收，尤其是混跑和重载，不将“已写代码”视作“已验证”
3. 建立统一的物理列车身份和设备查询接口，补观察器过滤、列车信息及车站信息读取
4. 逐项补齐剩余时刻表指令、条件及关联的货物/旅客/显示功能
5. 最后处理跨维度整列迁移，并验证全系统闭环

## “完全兼容”的判定

只有在约定范围内的原版铁路功能都有对应实现，所有上述验收场景通过，已知阻断问题关闭，并明确独立物理组装与原版组装的对应关系后，才可使用“完全兼容”的表述。当前既有明确未实现项，也有待验证项，因此不提供容易误导的完成百分比。
